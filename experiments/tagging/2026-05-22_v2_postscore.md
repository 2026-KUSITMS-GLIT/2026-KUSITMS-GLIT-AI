  LLM 이 `#문제정의·#직군간협업·#산출물전달`. accept 의 `#직군간협업·#문제정의` 는
  맞췄지만 기술 리서치 자체는 못 잡고 디자이너에게 자연스러운 협업·전달 쪽으로 빠졌다.

### 8. corrective 3건 원인은 백틱뿐 아니라 다양하다

  정규식이 trailing 텍스트 못 잡아 JSON 파싱 실패.
- **D-DA-01**: triple backtick + 풀 외 `#비교분석` (풀에 없는 단어 생성).
- **D-PA-03**: 코드블록 없이 7개, 그런데 풀 외 `#상태관리` 포함.

5/18 측정의 "백틱 strip 만 보강하면 0건" 결과와 달리, 새 데이터에서는 백틱뿐 아니라
LLM 의 풀 외 태그 생성도 corrective 트리거가 된다. 다만 3/48 이라 운영상 부담은 없음.

## 결정

1. **v2 유지하면서 v3 로 진입.** must 72.7% 는 5/17 v1 baseline 의 53% 보다 명백히
   좋고, 새 metric 으로도 v2 가 합리적 수준에 와 있음을 확인. corrective 6%, 비용·지연
   변동 없음.

2. **v3 의 후보 갯수 확장 (5~7 → 7~10) 이 accept 회수 개선의 가장 큰 lever 로 보임.**
   풀외 21% 중 일부는 더 뽑으면 accept 안에서 잡힐 가능성이 있다. 측정해 봐야 알지만
   v3 우선순위 1.

3. **직군 모호 케이스 보강이 v4 의 `primaryCategory` 부스트 보다 먼저 다뤄야 할 문제로
   보인다.** P-PA-04, DS-DA-04 의 must 0% 는 가중치 신호가 정답에 역행하는 케이스고,
   v3 의 tie-break (LLM 응답 순서 약가중) 이 일부 도움 될 수도 있지만 충분치 않을 수
   있다. v3 결과 보고 별도 보강 로직 검토.

4. **LLM_ERR 4건은 v3 측정 전에 한 번만 재돌려 본다.** rate limit 일시 장애로 보이지만
   다음 측정에서도 끝에 몰리면 같은 일이 또 생길 수 있다. 케이스 순서 셔플 또는 호출
   간격 조정 (`asyncio.sleep`) 도 옵션.

5. **풀 외 비율은 코드 후처리 범위에서는 다루지 않고 추적 metric 으로만 둔다.** 프롬프트
   개선이나 accept set 확장은 별개 트랙으로 검토.
